# 배포 설정 및 재검증

운영 실행 시 `SPRING_PROFILES_ACTIVE=prod`를 지정한다. 운영 프로필은
`ddl-auto=validate`를 사용하므로 스키마 변경을 검토하고 별도로 적용한 뒤 실행한다.
로컬 개발은 기존 `update` 정책을 유지한다.

필수 Secret/환경변수는 `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `TOUR_API_KEY`,
`WEATHER_SHORT_TERM_API_KEY`, `WEATHER_MID_TERM_API_KEY`, `KAKAO_REST_API_KEY`,
`KAKAO_CLIENT_SECRET`, `KAKAO_REDIRECT_URI`, `FRONTEND_ORIGINS`다. 동물등록 조회 기능에는
`ANIMAL_REGISTRATION_API_KEY`를 추가한다. `.env.example`은 참고 파일이며 Spring Boot가
자동으로 읽지 않는다. 실행 환경 또는 배포 Secret 관리 기능으로 주입한다.
기존 로컬 `application.yml`은 Git 제외 대상이었다. 이번에 비밀값 기본값을 제거하고
설정을 추적 가능하게 바꿨다. 이전 비밀번호/API 키의 노출 이력은 별도로 확인하고,
노출된 값은 발급처에서 교체한 뒤 새 값만 배포 환경에 주입한다.

운영 세션 쿠키는 `HttpOnly=true`, `Secure=true`, `SameSite=Lax`가 기본이다.
프런트와 API를 같은 사이트의 HTTPS 도메인(예: app.example.com/api.example.com)으로
배치하고 `FRONTEND_ORIGINS`에는 정확한 프런트 origin을 쉼표로 구분해 넣는다.
서로 다른 사이트를 쓰는 경우에만 `SESSION_COOKIE_SAME_SITE=none`을 검토한다.
세션에 연결된 CSRF 토큰을 사용하며, 프런트 공통 API 클라이언트가 변경 요청 전에
`GET /api/auth/csrf`로 토큰을 받고 `X-CSRF-TOKEN` 헤더에 넣는다. 로그인·계정 연결 성공 시
세션 ID와 토큰을 갱신한다. 클라이언트는 `CSRF_INVALID` 응답에만 토큰을 새로 받아 한 번 재시도한다.
권한 오류나 서버 오류에는 변경 요청을 자동 재시도하지 않는다.
별도의 API 클라이언트도 같은 세션 쿠키와 CSRF 헤더를 보내야 한다.
교차 사이트 구성에서는 브라우저의 제3자 쿠키 제한을 실제 환경에서 확인해야 한다.
운영 HTTP Origin, 비보안 쿠키, OAuth 콜백에 부적합한 `SameSite=Strict`는 시작 시 거부한다.

`KAKAO_REDIRECT_URI=https://api.example.com/login/oauth2/code/kakao`처럼 실제 API 도메인의
HTTPS 콜백을 명시한다. 카카오 콘솔에도 정확히 같은 값을 등록한다. 이 주소는 프록시의
Host/전달 헤더로부터 추정하지 않는다. 실제 배포 주소는 아직 확정되지 않았으므로 예시 도메인을
운영 설정으로 사용하지 않는다.

프런트는 빌드할 때 `VITE_API_URL`에 경로 없는 API origin을 지정한다.
예: `https://api.example.com`. 모든 API와 카카오 로그인 시작 주소가 이 값을 공유한다.
누락·공백·origin 형식 오류는 빌드 오류로 처리한다. `.env.local`의 로컬 주소가
운영 빌드에 들어가지 않도록 CI에서 운영 값을 명시한다. `VITE_KAKAO_MAP_KEY`도 지정하고
카카오 콘솔에 운영 도메인 및 리다이렉트 URI를 등록한다.

맹견 전용 조건은 원문과 대상 견종을 보존한다. 기존 `DogBreed.isDangerous()` 분류상
일반견은 해당 준비물에서 제외하고, 맹견에게는 적용하며, 견종 미등록은 확인 필요로 처리한다.
모든 반려견에게 명시된 입마개 규정은 계속 적용한다.

2026-09-08에 실제 KTO 상세 API를 3건 조회했다. 응답을
`backend/src/test/resources/compatibility/kto-2026-09-08.json`에 보관하고,
실제 매퍼 → 원문 어댑터 → 파서 → 판정기를 통과하는 회귀 테스트에서 사용한다.
이 테스트는 일반견/맹견/미등록, 원문 보존, 레스케이프의 9kg/10kg 경계를 검증한다.

검색 페이지는 KTO의 전체 결과를 수집한 뒤 문화정보원 결과와 중복 제거하여 나눈다.
KTO와 일치하는 문화정보원 장소는 KTO ID와 규정을 유지하고 문화정보원 메타데이터를 덧붙인다.
`totalCount`는 중복 제거 후 결과 수다. 주변 검색은 두 출처를 합쳐 거리순으로 정렬하고
좌표가 없거나 반경 밖인 장소는 제외한다. 문화정보원 CSV에는 KTO 시군구 코드가 없으므로
시군구 코드가 지정된 지역 검색에는 광역 지역의 CSV 장소를 무분별하게 추가하지 않는다.

합성 결과는 정확한 검색 좌표·반경 또는 지역 조건별로 2분간 재사용하며 페이지·크기 변경에도
같은 결과를 사용한다. 최대 16개 결과를 보관하고 동시 결과 생성은 4건으로 제한한다.
첫 검색은 KTO 페이지 수만큼 조회가 필요하며, 제공기관 결과가 중간에 바뀌거나 불완전하면
일부 결과를 완전한 목록으로 반환하지 않고 재시도 안내를 반환한다. 요청당 외부 페이지 상한은
100페이지(10,000건)다. 캐시 만료·서버 재시작·다중 서버 간에는 새 스냅샷이므로 공급자 데이터가
변경되면 페이지 경계도 바뀔 수 있다. 장시간 목록 탐색에는 처음부터 재검색한다.
프런트는 현재 표시 개수와 전체 개수를 구분하고 새 검색 시작 시 이전 요청을 취소한다.

검증 명령:

- 백엔드 자동 테스트: `./gradlew test --offline`
- 프런트 API 클라이언트 테스트(Node 24): `npm test`
- 프런트 빌드: `npm run build`
- 실제 반경 검색: `./gradlew verifyNearbyPagination` (`TOUR_API_KEY` 필요, 최대 15회 조회,
  DB·계정 데이터 변경 없음). 5/10/20/30km의 모든 페이지에서 중복·총 건수·반경 간 포함 관계를 검사한다.

운영 프로필의 실제 Set-Cookie 헤더는 내장 서버 테스트로 확인한다.
OAuth 테스트는 제어된 제공기관 서버로 인증 시작 → code 교환 → 사용자 정보 → 콜백 → 세션 →
`/api/auth/me`를 검증하며, 실제 카카오 계정 인증과 구분한다.

배포 전 추가 검증:

- 새 설정을 주입한 서버에서 실제 KTO 2586384, 264311, 264353을 다시 조회하고
  일반견/맹견/미등록의 판정 및 원문 보존을 확인한다.
- 실제 HTTPS 도메인에서 Set-Cookie, 로그인 유지, 로그아웃과 CORS를 확인한다.
- 카카오 사용자 인증 이후 콜백과 `/api/auth/me`까지 확인한다.
- 회원가입·로그인·반려견·장소·일정 화면과 모바일/태블릿 레이아웃을 확인한다.
- 실제 배포에서 캐시 만료·다중 인스턴스 운영 시 목록 갱신 동작을 확인한다.
  단일 페이지의 반경별 포함 관계는 페이지 제한 때문에 보장하지 않는다.

기존 검증용 계정과 데이터는 이 수정 작업에서 삭제하지 않는다.
